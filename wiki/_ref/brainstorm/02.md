# Simplificação de Frações em Sub-Nanosegundos: O Que Isso Significa no Código

Simplificar uma fração `n/d` significa dividir ambos pelo `MDC(n, d)`. No código, o "caminho ingênuo" é algo assim:

```rust
#[derive(Copy, Clone)]
struct Frac { num: u32, den: u32 }

fn simplify(f: Frac) -> Frac {
    let g = gcd(f.num, f.den);      // algoritmo de Euclides
    Frac { num: f.num / g, den: f.den / g }
}

fn gcd(mut a: u32, mut b: u32) -> u32 {
    while b != 0 { let t = b; b = a % b; a = t; }
    a
}
```

Esse código tem **três divisões inteiras** (uma por iteração do Euclides, mais duas no final). Em x86-64 moderno, `DIV` tem latência de **~20-30 ciclos** e throughput de **~6-10 ciclos**. Ou seja: mesmo no melhor caso, você está na casa de **dezenas de nanosegundos por fração**. Sub-ns por fração, com essa estrutura, é impossível.

Para chegar ao sub-ns, você precisa mudar **o que** está sendo medido e **como** o cálculo é feito. Vou separar em duas frentes: *latência* e *throughput*.

---

## 🧠 A Distinção Crucial: Latência vs. Throughput

Sub-ns **por operação** quase nunca significa que uma única simplificação termina em menos de 1 ns. Um ciclo a 3 GHz já é ~0,33 ns, então você teria 1-3 ciclos para fazer tudo — impossível com divisão.

O que se atinge na prática é **sub-ns por fração em regime de fluxo (throughput)**:

- Uma simplificação isolada leva, digamos, 20 ns de latência.
- Mas o pipeline processa 64 frações em paralelo (SIMD) com 4 unidades de execução → **~0,3 ns por fração**.

Toda a otimização real vai nessa direção: **processar muitas frações ao mesmo tempo**, não acelerar uma só.

---

## 📐 Estratégias por Largura de Bits

### 1. `u8` — Tabela de consulta direta (LUT)

Se `num, den ∈ [0, 255]`, você pode indexar diretamente uma tabela pré-computada:

```rust
// 256 * 256 entradas de u16 = 128 KB.
// Cabe no L2. Uma leitura = ~4-14 ciclos, sem divisão alguma.
static SIMPLIFIED: [[u8; 256]; 256] = build_table();

#[inline(always)]
fn simplify_u8(f: Frac8) -> Frac8 {
    let packed = SIMPLIFIED[f.num as usize][f.den as usize];
    Frac8 { num: packed >> 8, den: packed & 0xFF }
}
```

Com isso, cada simplificação custa **um load** — algo entre 4 e 14 ciclos de latência, ou **~1-2 ciclos de throughput**. Se você processar 8 frações com AVX-512 usando `vpgatherdd`, cada uma sai em **fração de nanossegundo**.

Alternativa mais compacta: tabela de MDC `[[u8; 256]; 256]` (64 KB, cabe no L2) + duas divisões. Mais lento que a LUT direta, mas 4x menor.

### 2. `u16` — Tabela de MDC + divisão por recíproco

Para `u16`, a LUT direta teria 4 GB — inviável. Mas a LUT de MDC tem 256×256 = 64 KB se você trabalhar com bytes, ou 65536×65536 se for `u16` — também inviável.

A saída é **Binary GCD (Stein)** branchless, que substitui divisão por shifts e subtrações:

```rust
#[inline(always)]
fn gcd_u16(mut u: u16, mut v: u16) -> u16 {
    if u == 0 { return v; }
    if v == 0 { return u; }
    let shift = (u | v).trailing_zeros();
    u >>= u.trailing_zeros();
    loop {
        v >>= v.trailing_zeros();
        if u > v { core::mem::swap(&mut u, &mut v); }
        v -= u;
        if v == 0 { return u << shift; }
    }
}
```

Cada iteração custa ~2-4 ciclos (shift, compare, subtract, branch). Para números pequenos, o número de iterações é baixo. Ainda assim, o **branch** interno quebra o pipeline.

Para eliminar o branch, use uma versão com `cmov`/`select`:

```rust
loop {
    v >>= v.trailing_zeros();
    let (lo, hi) = if u < v { (u, v) } else { (v, u) };
    v = hi - lo;
    if v == 0 { return lo << shift; }
    u = lo;
}
```

O compilador gera `cmov` em vez de `jmp`. Isso mantém o pipeline cheio.

### 3. `u32`/`u64` — Binary GCD branchless + divisão por recíproco

Para `u32`, o Binary GCD continua bom, mas a divisão final `num/g` e `den/g` ainda é cara. Aqui entra a **divisão por recíproco** (Libdivide):

- Se `g` fosse constante, o compilador já faria isso sozinho (multiplicação + shift).
- Como `g` é variável, você precisa calcular o recíproco em tempo de execução — o que **não compensa** para uma única divisão.
- **Mas compensa se você dividir muitos números pelo mesmo `g`** — o que é comum quando várias frações compartilham o mesmo denominador.

```rust
// Se você tem N frações com o mesmo denominador d,
// e um MDC comum g, calcule o recíproco uma vez:
let recip = libdivide::DividerU32::new(g);
// e use para todas as N divisões:
let new_num = recip.divide(f.num);
```

### 4. Compile-time — Se as frações são conhecidas em `const`

Se as frações são conhecidas em tempo de compilação, use `const fn` com `gcd` recursivo. O compilador pré-computa tudo e o binário só contém constantes. Custo em runtime: **zero**.

```rust
const fn simplify_const(num: u32, den: u32) -> (u32, u32) {
    let g = gcd_const(num, den);
    (num / g, den / g)
}

const HALF: (u32, u32) = simplify_const(50, 100); // (1, 2) em tempo de compilação
```

Isso é sub-ns trivialmente — é literalmente um load de constante.

## ⚡ Processamento em Lote com SIMD

Aqui está o segredo real. Se você tem um **stream de frações** para simplificar, SIMD muda o jogo.

### Binary GCD vetorizado (AVX-512)

AVX-512 tem `vplzcntd` (count leading zeros) e `vptzcntd` (trailing zeros) por lane. Isso permite implementar Binary GCD em 16 lanes `u32` simultaneamente:

```rust
use core::arch::x86_64::*;

#[target_feature(enable = "avx512f,avx512cd")]
unsafe fn gcd_simd_16(u: __m512i, v: __m512i) -> __m512i {
    // ... shift inicial, loop com vptzcntd, vpsubd, vpminud/vpmaxud
    // 16 MDCs em paralelo
}
```

Cada iteração processa 16 frações. O número de iterações é `max(log2(num_i))` — geralmente 8-16 para `u32`. Total: **~16 × 16 = 256 ciclos para 16 frações** = **~16 ciclos por fração** = **~5 ns por fração**. Longe de sub-ns, mas 20-50x melhor que o loop escalar.

### Melhor: LUT de MDC vetorizada com `vpgatherdd`

Se você tem uma LUT de `u16` (65536 entradas), pode fazer 16 gathers por instrução. Mas gathers são lentos em muitas microarquiteturas. Melhor usar LUT pequena (256 entradas) e processar apenas `u8`.

### O ponto ideal: LUT direta + AVX-512 `vpermi2b`

Se as frações são `u8` e você usa **VBMI** (AVX-512), pode indexar uma tabela de 128 KB com `vpermi2b` em 64 lanes ao mesmo tempo. **64 simplificações por instrução**. A ~5 ciclos por instrução, isso é **0,08 ciclos por fração** — ordens de magnitude abaixo de 1 ns por fração.

## 🔄 Reestruturação Algorítmica

Para sequências de operações (ex: somar muitas frações), não simplifique a cada passo. Isso é o erro mais comum.

**Errado (simplifica a cada passo):**
```
(a/b + c/d) + e/f + ...
```

**Certo (simplifica só no final ou em pontos estratégicos):**
```
num = a*d*f + c*b*f + e*b*d
den = b*d*f
simplify uma única vez no final
```

Isso reduz `N` simplificações para `1`, e o custo dominante passa a ser as multiplicações — que são SIMD-friendly.

Quando os denominadores explodem, use o truque do **MDC acumulado**: mantenha `g = gcd(g, novo_den)` a cada passo e divida apenas no final.

## 📊 Expectativas Realistas

| Abordagem | Latência por fração | Throughput por fração |
| :--- | :--- | :--- |
| Euclides escalar `u32` | ~30-50 ns | ~10 ns |
| Binary GCD escalar branchless `u32` | ~15-25 ns | ~5 ns |
| LUT direta `u8` escalar | ~2-4 ns | ~1 ns |
| SIMD Binary GCD `u32` (16 lanes) | — | **~5 ns** |
| SIMD LUT `u8` com `vpermi2b` (64 lanes) | — | **~0,1 ns** ✅ |
| Compile-time (const) | **0 ns** | **0 ns** ✅ |

Sub-ns **por fração** só é realista em três cenários:
1. **Frações `u8` processadas em lote com SIMD** (o cenário mais realista para "cálculo aritmético").
2. **Frações conhecidas em tempo de compilação**.
3. **Medição de throughput com paralelismo massivo** (muitos núcleos + SIMD).

Sub-ns de **latência** para uma única simplificação arbitrária de `u32` é fisicamente impossível — a divisão inteira sozinha já custa mais que isso.

## 🛠️ Recomendação de Stack

Se eu fosse implementar isso hoje:

1. **Se `u8`**: LUT de 128 KB + AVX-512 VBMI. Melhor caso absoluto.
2. **Se `u16`**: Binary GCD branchless + processamento em lote com `pulp`.
3. **Se `u32`/`u64`**: Binary GCD branchless + SIMD com `std::arch` (AVX-512 `vplzcntd`/`vptzcntd`).
4. **Compile com** `-C target-cpu=native -C codegen-units=1 -C opt-level=3`.
5. **Meça com** `cputicks` ou `pbench` (RDTSC), nunca com `Instant`.
6. **Considere `libdivide`** se houver divisões repetidas por um mesmo `g`.
7. **Evite `num-rational`** — não é otimizado para esse nível.

Se você me disser a **largura de bits** das frações (u8? u32? u64? bignum?) e se elas vêm em **lote** ou **isoladas**, posso escrever o código concreto para o seu caso.
